# 表格列类型判定清单

## 1. 目的

这份清单用于联调自然语言生成和截图生成的表格时，快速判断某一列为什么会落成当前单元格样式，以及出现误判时应该先看哪条规则。

当前表格列类型不是单一来源决定，而是三层共同作用：

1. AI 返回的 `columnTypes` 或单元格对象结构
2. `table.skill.ts` 的本地推断与纠偏
3. `code.ts` 的渲染与回读归一化

因此，同一列“看起来应该是什么”不一定等于最终实际落地类型。

## 2. 当前支持的主要列类型

1. `Text`
2. `Avatar`
3. `TypeTag`
4. `StatusTag`
5. `Number(unit)`
6. `ActionText`
7. `ActionIcon`
8. `Input`
9. `Select`

主映射入口在 [table.skill.ts](file:///Users/bytedance/VEDUIAgent/src/engine/skills/table.skill.ts) 的 `inferColumnType()` 与 `tableTypeToComponentId()`。

## 3. 判定优先级

当前列类型推断的主顺序是：

1. 操作列表头
2. 时间/日期列
3. Avatar 列
4. 视觉 Tag 列
5. 普通 TypeTag 列
6. 通用 Tag 信号列
7. `Number(unit)`
8. 内容像操作列
9. 默认 `Text`

所以很多误判都不是“最后一步出错”，而是更早的高优先级规则先命中了。

## 4. 各类型判断口径

### 4.1 `Text`

适用场景：

1. 普通文本列
2. 时间/日期列
3. 编号、编码、IP、地址、长标识列
4. 任何不满足其它类型稳定信号的列

当前已明确强制回 `Text` 的内容：

1. 日期/时间，如 `2026-01-15`、`10:30`
2. IP/地址，如 `10.0.0.1`
3. 多小数点文本，如 `22.22.22`
4. 长标识文本，如较长的 `topic/key/id` 风格字符串

### 4.2 `Avatar`

适用场景：

1. 表头明显是人相关字段，如 `负责人`、`创建人`、`成员`、`用户`、`姓名`
2. 整列多数值像真实人名
3. 单元格对象里带明确用户对象字段，如 `avatar`、`userName`

当前规则特点：

1. 中文名不是“任意 2 到 4 个中文”就算
2. 需要更像真实姓名，包含姓氏判断
3. `服务名称`、`状态`、`分组`、`时间`、`IP/地址`、`操作` 这类表头会被排除

高风险误判：

1. 普通中文短词被误当人名
2. 圆点/徽标 + 文本被 AI 误写成头像对象

### 4.3 `TypeTag`

适用场景：

1. 非状态语义的短标签列
2. 灰框标签、浅底标签、pill/chip/badge 外观
3. 地域、环境、分组、类别等短文本列

当前规则特点：

1. 视觉 Tag 默认优先落 `TypeTag`
2. 纯字符串短文本列也可能被兜底升成 `TypeTag`
3. 一整列如果已经判成 `TypeTag`，单个 cell 不应再漂成 `StatusTag`

高风险误判：

1. 本来是普通文本，但因为短文本占比高被升成 `TypeTag`
2. AI 纯看列名，误把并非标签的列写成 Tag

### 4.4 `StatusTag`

适用场景：

1. `启用/禁用/成功/失败/运行中/已停止`
2. 表头明确是 `状态/status/state`
3. 对象里带明确状态语义，如 `statusSemantic/statusTheme/tagKind=status`

当前规则特点：

1. 只有有明确状态语义才应该走彩色状态标签
2. 单纯短文本或视觉标签，不应自动走 `StatusTag`

高风险误判：

1. 普通标签对象里混入 `state/color/theme` 字段，导致单个 cell 漂成彩色状态 Tag

### 4.5 `Number(unit)`

适用场景：

1. 金额、比例、容量、时长、单位数值列
2. 同列多数值可以稳定解析成“数字 + 可选单位”

当前规则特点：

1. 只认一个小数点
2. 日期时间不算
3. IP 不算
4. 多小数点文本不算
5. 编号、编码、地址类表头会被排除

示例：

1. 会算：`35%`、`1.5GB`、`120ms`、`1234`
2. 不算：`2026-01-15`、`10.0.0.1`、`22.22.22`

高风险误判：

1. 版本号、IP、日期被拆成“数值 + 单位”
2. OCR 把文本切坏后，前半段长得像数字

### 4.6 `ActionText`

适用场景：

1. 短操作短语，如 `编辑 删除`
2. 表头就是 `操作`
3. 单元格内主要是短动作词

高风险误判：

1. 长标识里包含 `settings/open/close` 等词
2. 文案本身不是操作，只是包含动作词片段

## 5. 自然语言生成 vs 截图生成

### 5.1 自然语言生成

主要风险：

1. AI 直接给错 `columnTypes`
2. AI 给错对象结构，比如把站点写成 `Avatar`
3. AI 没给结构化 Tag 对象，只给了纯字符串

优先排查：

1. 原始 `draw_table` payload 的 `columnTypes`
2. 单元格对象里有没有 `appearance/tagKind/statusSemantic`

### 5.2 截图生成

主要风险：

1. 视觉误读
2. Tag 样式被提纯成普通字符串
3. 合并单元格没输出 `merges`
4. 圆形徽标 + 文本被误读成 Avatar

优先排查：

1. AI 是否输出了结构化 Tag 对象
2. AI 是否输出了 `merges`
3. 纯字符串列是否被本地兜底提升

## 6. 目前最容易出问题的边界

1. `Text` 和 `Avatar`
2. `Text` 和 `TypeTag`
3. `TypeTag` 和 `StatusTag`
4. `Text` 和 `Number(unit)`
5. `Text` 和 `ActionText`

这些都是当前联调时优先关注的高风险边界。

## 7. 推荐 Prompt 写法

### 7.1 推荐

1. 明确写“员工/负责人列使用头像单元格”
2. 明确写“状态列使用状态标签”
3. 明确写“地域/环境/分组列使用灰框标签”
4. 明确写“时间列使用普通文本，不要当数值单位”
5. 明确写“IP/地址/编号列使用普通文本”
6. 明确写“截图里视觉是 Tag 的单元格，请输出结构化对象而不是纯字符串”

### 7.2 不推荐

1. 只写“按截图复刻”，不说明 Tag/Avatar/时间列角色
2. 用列名硬编码所有样式判断
3. 把“有圆点图标”直接等同于 Avatar

## 8. 联调排查顺序

当某列类型不符合预期时，建议按这个顺序看：

1. 先看这列的业务角色：人名、状态、普通标签、数值、时间、操作、普通文本
2. 再看 AI 原始 payload 有没有显式 `columnTypes`
3. 再看 cell 是不是对象，是否带 `appearance/tagKind/statusSemantic/avatar`
4. 再看本地兜底是否把它提升或纠偏成了别的类型
5. 最后看 `code.ts` 回读时有没有把已有组件重新映射成别的类型

## 9. 当前已知风险结论

结论不是“现在完全不会错”，而是：

1. 最常见的误判场景已经收紧了一轮
2. 以后仍可能出现样式与预期不符
3. 但大多数问题会落在这份清单列出的边界里，而不是随机发生

因此，后续联调时优先用这份清单判断“它本质上属于哪一类误判”。
